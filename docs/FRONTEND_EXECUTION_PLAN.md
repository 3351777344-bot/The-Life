# 前端执行计划

更新时间：2026-05-18
适用分支：`Tilams`
负责人：Codex + 项目组前端成员

## 1. 目标定义

本计划面向 2026 年 6 月前的“初版完整产品”目标，核心不是继续堆页面数量，而是把现有 demo 收口成一个可演示、可联调、可继续迭代的前端产品。

本阶段前端总目标：

1. 跑通完整主流程：建模 -> 命轨 -> 衍化 -> 对比 -> 观心 -> 论道 -> 归途。
2. 统一前端状态结构，减少页面间逻辑割裂。
3. 抽离接口层，为后端联调预留稳定接入点。
4. 打磨终局报告和关键演示页，满足答辩与展示需求。
5. 在不推翻现有代码的前提下，逐步把 demo 逻辑升级为产品逻辑。

## 2. 当前项目判断

根据现有代码、项目文档和构建验证，当前项目状态如下：

1. 项目已经可以正常构建，说明工程基线可用。
2. 多视图主流程和大部分核心页面已经存在，适合在原基础上迭代，不适合推倒重来。
3. 当前代码更接近“高保真前端 demo”，还不是“完整可交付初版”。
4. 主要缺口不在页面数量，而在状态闭环、接口整合、结果回写、数据可信度和展示稳定性。
5. 打包体积偏大，后续需要做按页面或模块拆分优化。

## 3. 本阶段范围

### 3.1 必须完成

1. 主流程闭环。
2. 路线选择、属性变化、问答、终局报告之间的数据打通。
3. 基础接口层整理。
4. 终局报告页和反思页的产品化收口。
5. 基础错误态、加载态、空状态补齐。
6. 电脑端优先的稳定展示体验。

### 3.2 应该完成

1. 文档上传能力优化。
2. 属性计算规则整理。
3. 顾问问答上下文增强。
4. 本地存档与恢复体验整理。
5. 对比页和命轨页的交互细节优化。

### 3.3 可以后放

1. 名人模拟。
2. 多 Agent 深度协同。
3. 真正的视频生成链路。
4. 实时政策月更。
5. AI 口型同步和复杂角色动画。
6. 协作型功能和多人对比。

## 4. 分阶段计划

## 阶段一：前端接管与状态收口

目标：把当前代码从“能跑”整理成“可持续开发”。

重点任务：

1. 梳理 `App.vue` 中的集中状态。
2. 识别 demo 数据、真实业务数据、临时占位逻辑。
3. 统一消息结构、路线结构、属性结构、报告结构。
4. 补上最关键的流程统计和页面回写能力。

交付结果：

1. 前端主流程状态更清晰。
2. 关键页面能共享统一数据结构。
3. 后续接口整合的基础打好。

## 阶段二：主流程闭环

目标：让用户能完整走完一次产品体验。

重点任务：

1. 建模页输入影响后续路线生成。
2. 命轨页节点操作能够持续影响后续流程。
3. 衍化页路线选择与对比能回写属性。
4. 观心页正确展示属性、趋势和影响溯源。
5. 论道页顾问问答携带上下文。
6. 归途页生成完整终局报告。

交付结果：

1. 产品可完成一轮完整演示。
2. 终局页成为真实收口页面，不再只是静态展示。

## 阶段三：接口整合层

目标：让前端从本地 demo 逻辑平滑过渡到团队联调模式。

重点任务：

1. 抽离统一服务层。
2. 规范请求参数与返回字段。
3. 支持 mock / real 双模式切换。
4. 统一错误处理与兜底逻辑。

交付结果：

1. 前端页面不再直接耦合单一 demo 接法。
2. 后续和队友联调时修改范围更小。

## 阶段四：展示体验优化

目标：让初版产品更适合答辩、汇报和演示。

重点任务：

1. 统一视觉与文案细节。
2. 优化树状图、对比页、反思页、终局页的关键体验。
3. 处理空状态、边界状态和回退体验。
4. 确定最稳定的演示路径。

交付结果：

1. 页面更像成品，而不是拼接 demo。
2. 核心展示流程更稳。

## 阶段五：性能与收尾

目标：完成六月前的交付级收口。

重点任务：

1. 处理主包过大问题。
2. 做按页面懒加载或模块拆分。
3. 检查控制台错误和状态污染。
4. 做最终构建验证。

交付结果：

1. 代码结构更稳定。
2. 构建结果更适合交付与继续维护。

## 5. 当前默认开发顺序

后续代码工作按下面顺序推进：

1. 继续收口 `App.vue` 和页面间共享状态。
2. 整理路线与属性变化规则。
3. 处理终局报告和反思页的闭环细节。
4. 抽服务层，准备接口联调。
5. 优化文档上传和多模态模块的兜底行为。
6. 再做性能优化和页面拆包。

## 6. 质量要求

每一轮修改都需要满足：

1. 项目可重新构建。
2. 不破坏当前主流程。
3. 尽量减少一次改动的影响面。
4. 每次改动留下独立变更记录文件。
5. 对用户可见行为变化做明确说明。

## 7. 变更记录规则

从本计划生效开始，每一轮代码修改都生成一份独立记录文件，存放在：

`docs/change-logs/`

命名规则：

`YYYY-MM-DD-round-XX.md`

每份记录至少包含：

1. 本轮目标。
2. 修改文件列表。
3. 改动内容摘要。
4. 对产品行为的影响。
5. 构建或验证结果。

## 8. 计划使用说明

1. 本文件作为后续前端工作的基准计划。
2. 若后续计划发生变化，应优先更新本文件，再继续开发。
3. 变更记录文件用于描述“本次改了什么”，本文件用于描述“整体准备怎么做”。
